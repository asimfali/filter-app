# Решения и договорённости

Общая память проекта для агентов (opencode и Claude Code) и людей. Сюда попадает только то, что не
выводится из кода и пригодится в будущих сессиях: принятые решения, договорённости, причины отказа
от вариантов, особенности окружения.

## Формат записи

Дописывай **в конец** файла — писать могут два агента параллельно (opencode и Claude Code), поэтому
файл append-only: существующие записи не редактируй и не удаляй.

    ## YYYY-MM-DD — краткая тема

    - Контекст: почему возник вопрос.
    - Решение: что решили.
    - Следствия: что теперь важно помнить, что сломается при ином решении.

Не записывай секреты, пароли, токены и то, что уже есть в `CLAUDE.md` / `.claude/CLAUDE.md`. Быстро
добавить запись — команда `/remember <суть>`.

## 2026-11-18 — Экран «Дилеры»: каркас до контракта портала

- Контекст: портал делает справочник дилеров (`/api/v1/dealers/`), filter-app — интерфейс заполнения
  (DEALERS_CHECK_PLAN.md, часть 3). Контракт и точные RBAC-коды придут письмом позже.
- Решение: экран собран на предположениях, но все места, зависящие от контракта, собраны в
  `src/api/dealers.js` (путь, query-параметры, ключ записи, способ отмены авторизации) и в
  `src/utils/permissions.js` (`dealers.view` / `dealers.write` / `portal.page.dealers` — предварительные).
  Отмена авторизации — `PATCH {is_active: false}`, ключ записи — ИНН; код `D#####` только на чтение.
- Следствия: когда придёт контракт, править `src/api/dealers.js` и коды прав, страницу/модалку —
  только если поменяется набор полей. Ответственность за код дилера — на портале; во фронте его
  нельзя редактировать и при создании он пустой («присвоит портал»).

## 2026-11-18 — Дилеры: сверка с реальным контрактом портала (правка предыдущей записи)

- Контекст: портал уже отдал `apps.dealers`, предварительные предположения не совпали.
- Решение: путь — `/api/v1/dealers/dealers/` (include + префикс роутера); список приходит
  массивом без конверта (нет пагинации), create/update/revoke/restore — конвертом `{success, data}`;
  ключ записи — `id`, не ИНН (ИНН редактируемый); отмена авторизации — `POST <id>/revoke/`,
  восстановление — `POST <id>/restore/` (поле `reason` уходит в `note`); право одно —
  `portal.dealers.write`, бэкенд требует его и на чтение.
- Следствия: фронт фильтрует и страницует список на клиенте, пока портал не включит
  `filter_backends`/пагинацию; `?search/?is_active` уже отправляются и начнут работать без правок.
  Когда ответ станет `{count, results}`, клиентская ветка отключится сама (проверка на массив).

## 2026-11-18 — Дилеры: путь без двойного сегмента и импорт из xlsx

- Контекст: портал `dev@6a12ecf` убрал префикс роутера (`router.register(r'')`), поэтому API
  переехал с `/api/v1/dealers/dealers/` на `/api/v1/dealers/`. Одним коммитом добавлен импорт
  справочника из xlsx (аналог PDF/DXF-кнопок).
- Решение: `BASE` в `src/api/dealers.js` — `/api/v1/dealers`; старый двойной путь больше не
  поддерживается (портал поменял его сразу и без промежуточного периода).
  Импорт: `POST /dealers/import/` (multipart `file=.xlsx`) → `{data: {task_id}}`, затем опрос
  `GET /dealers/{taskId}/import-status/` (в пути — id **задачи**, не дилера) каждые 2 с до
  `COMPLETED`/`FAILED`; поля `rows_total/created/updated/revoked/errors[{row, inn, error}]/result`.
  UI — кнопка «Импорт из xlsx» на экране дилеров (`DealerImportModal`), итог со счётчиками и
  таблицей битых строк, окно можно закрыть — задача продолжается на портале.
- Следствия: импорт требует работающего celery-воркера портала, иначе задача навсегда останется
  в `PENDING` (опрос крутится, пока окно открыто). Битая строка не валит импорт — она в `errors`,
  применённые строки остаются. Статистика перезагружается листом дилеров после завершения.

## 2026-11-18 — Сборка на Node 24 и `npm ci` в деплое

- Контекст: на сервере `tmdata` системный Node 18 (Ubuntu 24.04), а dev-зависимости фронта
  требуют `>= 20` (`@tailwindcss/oxide`, `vitest`, `jsdom`). Плюс `deploy_frontend.sh` собирал через
  `npm install --legacy-peer-deps`, который переписывал `package-lock.json` прямо в рабочем дереве
  (из lock выпадали peer-зависимости → следующий `npm ci` падал на `Missing: @testing-library/dom`).
- Решение: Node 24 ставится отдельно в `/opt/node24` (системный 18 не трогаем — на нём живёт
  `docgen` на :3000, чужое приложение); `deploy_frontend.sh` берёт `NODE_HOME` (по умолчанию
  `/opt/node24`), жёстко проверяет мажор `>= 20` и ставит зависимости через `npm ci`;
  `CLEAN_INSTALL=1` больше не удаляет lock. В репозитории — `.nvmrc` (24), `engines.node >= 20`,
  порядок описан в `docs/DEPLOY.md`.
- Следствия: сборка на сервере версионно совпадает с локальной (Node 24.22.3 против 24.13.1),
  EBADENGINE исчезли, lock на сервере всегда равен закоммиченному. Апгрейд тулчейна сделан:
  `vite 6.4.1 → 6.4.6`, `rollup 4.57 → 4.68`, `postcss 8.5.6 → 8.5.33` и транзитивные (lock).
  Остались 4 high в `npm audit --omit=dev` — цепочка `picomatch` (ReDoS) без выпущенного фикса;
  `npm audit fix` предлагает откатить vite на 6.2.7, это хуже (там свои CVE), поэтому ждём патч.

## 2026-11-18 — npm 11.19: `allowScripts` и EPERM на `rollup` при установке под запущенным dev-сервером

- Контекст: npm 11.19 блокирует install-скрипты зависимостей по умолчанию и после `npm install`
  пишет `2 packages have install scripts not yet covered by allowScripts` (`core-js`, `esbuild`),
  а в `cleanup` — `EPERM ... unlink node_modules\@rollup\.rollup-win32-x64-msvc-9v1pgPzx\rollup.win32-x64-msvc.node`.
- Решение: в `package.json` добавлено поле `allowScripts`: `esbuild@0.25.12: true` (postinstall —
  проверка/починка бинарника, нужен), `core-js: false` (postinstall только печатает рекламу).
  Ставить через CLI, не руками: `npm install-scripts approve esbuild`, `npm install-scripts deny core-js`;
  проверка — `npm install-scripts ls` → «No packages with unreviewed install scripts».
- Следствия: esbuild работает и с пропущенным postinstall — бинарник приходит из optional-зависимости
  `@esbuild/win32-x64`, `npm run build` зелёный, так что `npm ci` на npm ≥ 11.16 в деплое не сломается.
  Запись `esbuild@0.25.12` запинена: после апгрейда esbuild npm попросит подтвердить версию заново.
  EPERM в `cleanup` — не сбой установки: запущенный `vite` держал отображённый `rollup.win32-x64-msvc.node`,
  npm отодвинул старый каталог в `.rollup-...-<temp>` и не смог удалить замапленный файл. Лечится
  остановкой dev-сервера и `Remove-Item node_modules\@rollup\.rollup-* -Recurse -Force`; повторный
  `npm install` под живым dev-сервером повторит то же самое с новым временным каталогом.
  `npm audit` без улучшений: 9 high, всё замыкается на `picomatch@4.0.7` (ReDoS GHSA-fc5q-39xc-vjpf),
  в registry свежее тоже 4.0.7 — фикс не выпущен, `npm audit fix --force` по-прежнему делать нельзя.

- Массовое назначение группы: `bulk-group` у портала не запрашивали (418 записей — разовая

## 2026-11-18 — Дилеры: счётчики по статусам в шапке и сортировка «свежие сверху»

- Контекст: на экране «Дилеры» нужна сводка в шапке (сколько всего / активных / неактивных) и
  порядок по умолчанию «свежие сверху», а не по названию, как отдаёт портал.
- Решение: список запрашивается целиком, без `?search/?is_active` (`dealersApi.list({})`) — портал эти
  параметры всё равно не применяет (`DealerViewSet` без `filter_backends`, в `REST_FRAMEWORK` нет
  `DEFAULT_FILTER_BACKENDS` и `DEFAULT_PAGINATION_CLASS`), а счётчикам нужны все записи сразу.
  Сегменты «Все / Активные / Неактивные» со счётчиками — одновременно фильтр и сводка; считаются по
  всему справочнику, поиск их не сужает. Сортировка — `created_at || updated_at || letter_sent_at`
  по убыванию, дилеры без дат уходят в конец.
- Следствия: `DealerListSerializer` не отдаёт `created_at`/`updated_at`, поэтому «свежесть» сейчас —
  это «письмо отправлено»; как только портал добавит поля в список, сортировка переключится на дату
  записи без правок фронта. Если портал включит пагинацию (`{count, results}`), разбивку по статусам
  из ответа не вывести: панель покажет подписи без цифр, и понадобится отдельный endpoint со сводкой.

## 2026-11-18 — Дилеры: публикация записи (`is_published`) отдельно от публикации контактов

- Контекст: галочка «Публикация» в таблице дилеров правит только `contacts_published`, то есть
  блок телефонов/e-mail/сайта, а не запись целиком. Пользователю портала нужен рубильник «отдавать
  эту запись на сайт или нет» — так же, как у подразделений и товаров (`is_published`).
- Решение: колонка «Публикация» в таблице теперь про `is_published` (запись на сайте: карта «Сеть
  присутствия» + проверка дилера), а `contacts_published` переехал в форму дилера — там два флага
  подряд с пояснениями. В строке скрытые контакты помечены замком у e-mail, чтобы состояние было
  видно без второй галочки. Фронт PATCH-ит `is_published` точечно, без перезагрузки списка.
- Следствия: **на портале поля ещё нет** — фронт проверяет наличие ключа в ответе списка и, пока
  его нет, держит галочку выключенной с подсказкой (PATCH по неизвестному полю DRF молча игнорирует,
  галочка бы врала). Чтобы включить, на портале нужно: `is_published = BooleanField(default=True,
  db_index=True)` в `Dealer` (+миграция), поле в `DealerListSerializer`/`DealerCreateSerializer` и
  фильтр `is_active=True, is_published=True` в `build_dealers_payload()`; на сайте правок не нужно —
  отсутствующих в полной выгрузке он и так гасит по `dealers_complete`. Снятая галочка убирает
  дилера и с карты, и из проверки авторизации: в выгрузке одно состояние записи, отдельного
  «скрыть только с карты» нет.
## 2026-11-18 — Дилеры: обе галочки публикации в таблице, названия — как у полей портала

- Контекст: портал добавил `is_published` (`3f05595`, по ТЗ `status/TASK_PORTAL_DEALERS_PUBLISH.md`),
  а фильтр-приложение держало «публиковать контакты» только в форме и помечало скрытые контакты замком.
- Решение: в таблице две колонки с названиями из `verbose_name` модели — «Показывать на сайте»
  (`is_published`) и «Публиковать контакты» (`contacts_published`). Обе правятся точечным PATCH по
  одному полю (оптимистично, с откатом и текстом ошибки портала), замок у e-mail убран — состояние
  видно в колонке. В форме дилера те же две галки с пояснениями.
- Следствия: подписи в UI = `verbose_name` полей портала — при переименовании на бэке править и здесь.
  Флаги независимы (снятие «Показывать на сайте» не снимает «Публиковать контакты», как и в админке).
  У неактивного дилера обе галочки недоступны: выгрузка сайта — только активные. Если портал перестанет
  отдавать `is_published` в списке, колонка сама выключится с подсказкой (проверка на наличие ключа).
